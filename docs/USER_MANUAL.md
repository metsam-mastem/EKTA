# EKTA — راهنمای جامع کاربری (User Manual)

نسخه هدف: Runtime 0.2 + Operational Workspace 0.4  
مخاطب: کاربری که برنامه را نصب کرده و می‌خواهد دانش مهندسی را جست‌وجو، فیلتر و بررسی کند.

## 1. شروع سریع

1. مخزن EKTA را طبق USER_INSTALLATION.md اجرا کنید.
2. به http://127.0.0.1:8000/ بروید.
3. در کادر جست‌وجو یک اصطلاح، شناسه یا عبارت وارد کنید.
4. برای محدودکردن نتایج از هشتگ، فیلتر فیلدی یا پنل فیلترها استفاده کنید.
5. یک نتیجه را انتخاب کنید تا شناسنامه یا متن سند در پنل جزئیات نمایش داده شود.
6. برای بازگشت به فهرست، نتیجه دیگری انتخاب یا جست‌وجوی تازه اجرا کنید.

## 2. شناخت صفحه اصلی

Workbench سه بخش اصلی دارد:

### 2.1 نوار و معرفی
نام محصول، نسخه/وضعیت رابط و مسیرهای راهنما را نمایش می‌دهد.

### 2.2 پنل فیلتر و طبقه‌بندی
برای محدودکردن دامنه نتایج بر اساس قلمرو، حوزه تخصصی، لایه، نوع دانش، وضعیت و نوع نتیجه استفاده می‌شود. مقدارهای فیلتر از رجیستری‌ها و داده‌های مخزن می‌آیند.

### 2.3 پنل نتایج و جزئیات
نتایج به‌صورت کارت نمایش داده می‌شوند. هر کارت می‌تواند عنوان، شناسه، نوع رکورد، وضعیت، خلاصه، تکه متن تطبیق‌یافته و مسیر منبع را نشان دهد. با انتخاب کارت، جزئیات کامل‌تر در ناحیه نمایش باز می‌شود.

## 3. جست‌وجوی متنی

ورودی ساده:

~~~text
runtime
~~~

چند واژه:

~~~text
workflow runtime scheduler
~~~

واژه‌های آزاد به‌صورت AND بررسی می‌شوند؛ یعنی نتیجه باید همه واژه‌های جست‌وجوشده را در فیلدهای قابل جست‌وجو داشته باشد. این رفتار با جست‌وجوی OR متفاوت است.

جست‌وجو شکل‌های رایج عربی/فارسی «ی» و «ک» را نرمال‌سازی می‌کند؛ برای مثال تفاوت ي و ی یا ك و ک در تطبیق تا حدی رفع می‌شود.

## 4. عبارت دقیق

برای جست‌وجوی عبارت چندکلمه‌ای، آن را داخل کوتیشن قرار دهید:

~~~text
"workflow runtime"
~~~

عبارت دقیق باید به همان ترتیب در محتوای قابل جست‌وجو وجود داشته باشد. از کوتیشن دوتایی یا تکی استفاده کنید.

## 5. هشتگ

~~~text
#runtime
~~~

هشتگ‌ها از نام canonical، نام‌های جایگزین، شناسه‌ها، برچسب‌ها، طبقه‌بندی، عنوان‌ها، مسیر پوشه و برخی واژه‌های عنوان/محتوا مشتق می‌شوند. بنابراین لازم نیست همه هشتگ‌ها دستی در UI ساخته شوند.

نمونه‌ها:

~~~text
#runtime
#execution
#software-engineering
#platform-runtime
~~~

هشتگ یک نمایه واژگانی است؛ تضمین نمی‌کند دو مفهوم از نظر معنایی یکسان باشند.

## 6. فیلترهای فیلدی

| فیلتر | معنی | نمونه |
|---|---|---|
| id: | شناسه رکورد | id:EKTA-CON-000001 |
| territory: | قلمرو کلان | territory:software-engineering |
| domain: | حوزه تخصصی | domain:software-engineering |
| layer: | لایه مهندسی | layer:platform-runtime |
| type: | نوع دانش | type:concept |
| status: | وضعیت رکورد | status:PROPOSED |
| kind: | نوع نتیجه | kind:document |
| tag: | برچسب | tag:runtime |

مقدارهای چندواژه‌ای را در کوتیشن قرار دهید:

~~~text
territory:"software engineering"
~~~

نمونه ترکیبی:

~~~text
runtime territory:software-engineering layer:platform-runtime status:PROPOSED
~~~

شناسه‌های واقعی باید از رجیستری‌ها و رکوردهای مخزن برداشته شوند. نام نمایشی لزوماً همان ID فنی نیست.

## 7. ترکیب روش‌ها

همه اسناد درباره Runtime:

~~~text
#runtime kind:document
~~~

مفهوم‌های دارای وضعیت مشخص:

~~~text
kind:concept status:PROPOSED
~~~

جست‌وجوی یک مفهوم در حوزه نرم‌افزار:

~~~text
controller domain:software-engineering
~~~

شناسه دقیق:

~~~text
id:EKTA-CON-000001
~~~

## 8. کار با نتایج

هنگام بررسی کارت نتیجه:
1. عنوان و شناسه را بررسی کنید.
2. نوع نتیجه را تشخیص دهید: concept، document، taxonomy یا schema.
3. وضعیت را بخوانید؛ وضعیت دانش با وضعیت تأیید رابط یکسان نیست.
4. خلاصه و snippet را برای فهم محل تطبیق بخوانید.
5. مسیر منبع را ثبت کنید.
6. برای ادعای مهم، سند canonical یا منبع اصلی را باز کنید.

امتیاز جست‌وجو صرفاً رتبه‌بندی الگوریتم واژگانی است و معادل کیفیت علمی، اعتبار منبع یا میزان درستی مفهوم نیست.

## 9. خواندن شناسنامه مفهوم

شناسنامه مفهوم، رکورد canonical با شناسه پایدار است. بخش‌های مهم:
- تعریف و دامنه؛
- نام‌های مستعار؛
- حوزه‌ها و لایه‌ها؛
- نوع دانش و وضعیت؛
- عنوان‌ها و متن کامل؛
- روابط ورودی و خروجی در صورت وجود؛
- فایل منبع در مخزن.

اگر رابطه‌ای resolve نشده باشد، آن را رابطه قطعی تلقی نکنید. برای وضعیت گراف به RUNTIME_ARCHITECTURE.md مراجعه کنید.

## 10. خواندن سند

نتیجه‌های سند از فایل‌های منتخب مخزن ساخته می‌شوند. Document ID به مسیر فایل وابسته است و با تغییر مسیر ممکن است تغییر کند. برای ارجاع پایدار در گزارش یا تصمیم، URL فایل در Git و Commit مشخص را نیز ثبت کنید؛ Document ID به‌تنهایی شناسه دائمی دانش نیست.

## 11. فیلترهای کناری

می‌توانید ابتدا یک فیلتر مانند Territory یا Domain را انتخاب کنید و سپس جست‌وجو را اجرا کنید. برای بررسی نتایج جامع، فیلترهای ناخواسته را پاک کنید. اگر نتیجه‌ای دیده نمی‌شود:
- فیلترهای فعال را بررسی کنید؛
- واژه را بدون هشتگ امتحان کنید؛
- عبارت دقیق را به واژه‌های ساده تبدیل کنید؛
- نوع نتیجه را از kind:document به kind:concept یا برعکس تغییر دهید.

## 12. API برای کاربران فنی

| مسیر | کاربرد |
|---|---|
| GET /health | سلامت سرویس |
| GET /api/v1/overview | نمای کلی شمارگان اطلس |
| GET /api/v1/search?q=... | جست‌وجوی ترکیبی |
| GET /api/v1/facets | مقادیر فیلترها |
| GET /api/v1/concepts | فهرست مفاهیم |
| GET /api/v1/concepts/{id} | جزئیات مفهوم |
| GET /api/v1/documents/{id} | جزئیات سند با شناسه مشتق‌شده |
| GET /api/v1/taxonomy | رجیستری‌های طبقه‌بندی |
| GET /api/v1/graph | گراف و روابط |

مستندات تعاملی در /docs قرار دارد. APIهای کاوشگر GET و read-only هستند؛ مسیرهای Workspace برای staging، draft و backup از POST استفاده می‌کنند و همچنان از تغییر canonical جلوگیری می‌کنند.

نمونه:

~~~bash
curl "http://127.0.0.1:8000/api/v1/search?q=%23runtime"
~~~

برای پارامترهای دارای فاصله یا نویسه‌های غیر ASCII، URL-encoding را رعایت کنید.

## 13. میزکار عملیاتی\n\nاز نوار آدرس به `/workspace` بروید. میزکار شش بخش دارد: راه‌اندازی اولیه، خودآزمایی، مرکز ورود دانش، ویرایشگر پیش‌نویس، پشتیبان‌گیری/پیش‌نمایش بازیابی و مرکز مستندات. راهنمای کامل هر بخش در [WORKSPACE_GUIDE.md](WORKSPACE_GUIDE.md) است.\n\n- Import فقط Markdown/YAML/JSON متنی تا ۱ مگابایت را مرحله‌بندی می‌کند؛ انتشار خودکار ندارد.\n- ویرایشگر فقط پیش‌نویس محلی خارج از پوشه canonical می‌سازد.\n- Backup یک ZIP از مسیرهای منتخب می‌سازد؛ برای حفظ Git history همچنان clone کامل لازم است.\n- Restore فقط ZIP را اعتبارسنجی و در staging ذخیره می‌کند؛ فایل‌های اصلی بازنویسی نمی‌شوند.\n- Documentation Center فایل‌های Markdown زیر docs را به‌صورت متن نمایش می‌دهد.\n\n## 14. چه چیزی را نمی‌توان از UI انجام داد؟

در نسخه فعلی نمی‌توانید:
- فایل PDF، DOCX، XLSX، تصویر، صدا یا ویدئو را بارگذاری کنید؛
- ورودی مرحله‌بندی‌شده را به‌صورت خودکار به canonical منتشر کنید؛
- رکورد canonical را مستقیم در رابط ویرایش یا حذف کنید؛
- رابطه جدید بسازید؛
- منبع وب را خودکار crawl یا import کنید؛
- جست‌وجوی معنایی یا پرسش‌وپاسخ AI انجام دهید؛
- حساب یا فضای کاری چندکاربره بسازید.

برای افزودن دانش، از Git و قالب‌های مخزن استفاده کنید. مسیر رسمی در workflows/knowledge-intake.md و KNOWLEDGE_OPERATING_WORKFLOW.md آمده است.

## 15. اصول استفاده مسئولانه

- نتیجه جست‌وجو را پاسخ نهایی یا تأیید علمی تلقی نکنید.
- برای ادعاهای مهم، منبع اصلی و تاریخ/نسخه آن را بررسی کنید.
- محتوای PROPOSED را با VERIFIED اشتباه نگیرید.
- روابط unresolved را قطعی معرفی نکنید.
- محدودیت مجوز و حقوق نشر را رعایت کنید.
- اطلاعات محرمانه را در مخزن عمومی وارد نکنید.

## 16. گردش کار پیشنهادی روزمره

1. سؤال مهندسی را در یک جمله بنویسید.
2. واژه اصلی و مترادف‌هایش را جست‌وجو کنید.
3. با Territory و Domain محدوده را کوچک کنید.
4. شناسنامه‌های مرتبط را باز کنید.
5. روابط و اسناد مرجع را دنبال کنید.
6. منابع اولیه را مستقل ارزیابی کنید.
7. شکاف دانشی را در یک Work Item ثبت کنید.
8. اگر دانش جدید لازم است، از قالب canonical استفاده و از مسیر Git بازبینی کنید.
9. پس از اجرای آزمون یا آزمایش، شواهد را ثبت کنید.
