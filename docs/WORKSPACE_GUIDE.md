# راهنمای میزکار عملیاتی EKTA

**نسخه هدف:** Workbench Operational Suite v0.4  
**ورود:** پس از اجرای Runtime به نشانی `http://127.0.0.1:8000/workspace`

این میزکار شش ابزار را در یک سطح محلی گرد هم می‌آورد: راه‌اندازی اولیه، خودآزمایی، مرکز ورود دانش، ویرایشگر پیش‌نویس، پشتیبان‌گیری/پیش‌نمایش بازیابی و مرکز مستندات.

## 1. راه‌اندازی اولیه (Onboarding)

صفحه راه‌اندازی مسیر کار را به پنج مرحله تقسیم می‌کند: پیش‌نیازها، اجرای Runtime، خودآزمایی، ورود مرحله‌بندی‌شده دانش و حفاظت از داده‌ها. دکمه «اجرای بررسی اولیه» همان آزمون سلامت را اجرا می‌کند؛ وضعیت‌ها از API خوانده می‌شوند و صرفاً متن راهنما نیستند.

## 2. خودآزمایی (First-run Self-test)

مسیر `GET /api/v1/workspace/self-test` این موارد را بررسی می‌کند:
- Python 3.11 یا بالاتر؛
- وجود ریشه مخزن و README؛
- رجیستری‌های پایه Taxonomy؛
- پوشه مفاهیم canonical؛
- مرکز مستندات؛
- ماژول Runtime؛
- امکان نوشتن در فضای کاری محلی.

هر بررسی با PASS یا FAIL و جزئیات همراه است. PASS بودن این چک‌ها جایگزین آزمون کامل نرم‌افزار، بررسی صحت محتوا یا بازبینی امنیتی نیست.

## 3. مرکز ورود دانش (Knowledge Import Center)

فایل‌های Markdown، YAML و JSON با سقف ۱ مگابایت پذیرفته می‌شوند. فایل انتخابی یا متن واردشده در رابط به API ارسال می‌شود. YAML و JSON با parser امن بررسی می‌شوند؛ Markdown دارای Front Matter نیز از نظر ساختار اولیه بررسی می‌شود.

نتیجه در مسیر محلی `.ekta/workspace/imports/` مرحله‌بندی می‌شود. این عملیات:
- فایل canonical نمی‌سازد؛
- محتوای دانشنامه را تغییر نمی‌دهد؛
- رکورد را به‌طور خودکار منتشر یا ایندکس نمی‌کند؛
- جایگزین بررسی Schema، شناسه، Taxonomy، مجوز و منبع نیست.

انتقال از staging به مخزن canonical باید پس از بازبینی انسانی و از گردش کار Git انجام شود.

API: `POST /api/v1/workspace/import/preview` با بدنه JSON شامل `filename` و `content`.

## 4. ویرایشگر دانش (Knowledge Draft Editor)

ویرایشگر، شناسه پیشنهادی، نام canonical، حوزه‌ها، لایه‌ها و بدنه Markdown را دریافت می‌کند. پیش‌نویس با وضعیت PROPOSED و نسخه draft در `.ekta/workspace/drafts/` ذخیره می‌شود.

این ابزار:
- فایل‌های `encyclopedia/concepts/` را تغییر نمی‌دهد؛
- شناسه را در رجیستری سراسری رزرو نمی‌کند؛
- صحت معنایی یا کامل‌بودن Schema را تضمین نمی‌کند؛
- به‌تنهایی مجوز انتشار یا Commit نیست.

پیش از انتقال به دانشنامه، شناسه تکراری، Schema، Taxonomy، روابط، منابع و وضعیت ادعاها باید بررسی شوند.

API: `POST /api/v1/workspace/drafts`.

## 5. پشتیبان‌گیری و بازیابی

### ساخت پشتیبان
دکمه «ساخت بسته پشتیبان ZIP» از اسناد و اجزای مشخص پروژه snapshot می‌سازد. بسته در `.ekta/workspace/backups/` ذخیره و از طریق لینک همان صفحه دریافت می‌شود.

مواردی مانند `.git`، محیط مجازی، cache، node_modules، فایل‌های محیطی و کلیدها عمداً وارد بسته نمی‌شوند. این ZIP جایگزین clone کامل Git نیست؛ برای حفظ تاریخچه، Branchها و Commitها همچنان از `git clone --mirror` یا clone کامل استفاده کنید.

API: `POST /api/v1/workspace/backup` و `GET /api/v1/workspace/backups/{filename}`.

### پیش‌نمایش بازیابی
فایل ZIP با سقف ۲۰ مگابایت و حداکثر ۵۰۰۰ عضو بررسی می‌شود. مسیرهای absolute، مسیرهای دارای `..`، symlink و ساختار فاقد پوشه ریشه EKTA رد می‌شوند. بسته معتبر فقط در `.ekta/workspace/restore-staging/` ذخیره می‌شود.

**بازیابی خودکار و بازنویسی فایل‌های پروژه عمداً پیاده‌سازی نشده است.** پیش از هر بازیابی واقعی، باید محتوای بسته، نسخه مبدأ، تعارض‌ها و پشتیبان فعلی بررسی و یک گردش کار restore مستقل و آزمون‌شده طراحی شود.

API: `POST /api/v1/workspace/restore/preview`.

## 6. مرکز مستندات

فهرست فایل‌های Markdown داخل `docs/` از مخزن خوانده می‌شود. با انتخاب هر سند، محتوای خام Markdown در پنل نمایش داده می‌شود؛ رندر HTML یا اجرای اسکریپت داخل سند انجام نمی‌شود.

API:
- `GET /api/v1/workspace/docs`
- `GET /api/v1/workspace/docs/{document_path}`

## 7. فضای کاری محلی و پاک‌سازی

تمام داده‌های موقت در `.ekta/workspace/` قرار می‌گیرند و در Git نباید Commit شوند. برای پاک‌سازی می‌توان Runtime را متوقف کرد و پس از اطمینان از نیازنداشتن به پیش‌نویس‌ها، بسته‌های پشتیبان و ورودی‌های مرحله‌بندی‌شده، این پوشه را به‌صورت دستی آرشیو یا حذف کرد.

## 8. مدل امنیت و محدودیت‌ها

- Runtime به‌صورت پیش‌فرض باید روی loopback اجرا شود؛ این APIها برای دسترسی عمومی یا چندکاربره سخت‌سازی نشده‌اند.
- هیچ احراز هویت یا تفکیک کاربر وجود ندارد.
- ورودی فایل محدود به متن و فرمت‌های اعلام‌شده است؛ فایل اجرایی یا باینری ingest نمی‌شود.
- ZIP فقط اعتبارسنجی و مرحله‌بندی می‌شود؛ extract روی مسیر پروژه انجام نمی‌شود.
- پیش‌نویس و Import از canonical جدا هستند.
- پیش از انتشار، بررسی انسانی، اعتبارسنجی مخزن و آزمون CI لازم است.
