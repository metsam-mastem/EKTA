# استقلال EKTA از مکالمه و پروتکل بازیابی (Independence & Recovery)

## 1. آیا حذف چت به پروژه آسیب می‌زند؟

خیر، اگر اطلاعات ضروری در مخزن ثبت شده باشند. حذف یک گفت‌وگوی ChatGPT به‌خودی‌خود فایل‌ها، Commitها، Branchها، Issueها یا مستندات ثبت‌شده در GitHub را حذف نمی‌کند. EKTA مخزن مستقل GitHub دارد و Runtime محلی از فایل‌های مخزن استفاده می‌کند؛ برای اجرای آن به این مکالمه نیاز نیست.

اما اطلاعاتی که فقط در مکالمه مانده‌اند و هنوز به فایل، تصمیم، Issue یا Commit تبدیل نشده‌اند ممکن است از دسترس خارج شوند. هدف این پروتکل انتقال اطلاعات لازم به مخزن و حذف وابستگی عملیاتی به حافظه چت است.

## 2. مرز استقلال

| لایه | منبع حقیقت | وابستگی به ChatGPT |
|---|---|---|
| منشور و محدوده | docs/PROJECT_CHARTER.md | ندارد |
| چشم‌انداز و محصول | docs/VISION_AND_PRODUCT_STORY.md و PROJECT_OVERVIEW.md | ندارد |
| معماری دانش | KNOWLEDGE_ARCHITECTURE.md و taxonomy/ | ندارد |
| تصمیم‌ها | ADRهای پذیرفته‌شده در مخزن | ندارد |
| کد و Runtime | Git و Commitها | ندارد |
| شناسنامه‌ها و اسناد | فایل‌های canonical مخزن | ندارد |
| آزمون و کیفیت | tests/ و GitHub Actions | ندارد |
| برنامه ادامه کار | CONTEXT_CONTINUITY.md و Roadmap | ندارد |
| ایده‌های ثبت‌نشده در چت | مکالمه یا یادداشت بیرونی | ممکن است وابسته باشد |

مکالمه می‌تواند محیط همکاری باشد، اما نباید پایگاه داده، مخزن، دفتر تصمیم یا حافظه رسمی EKTA باشد.

## 3. سلسله‌مراتب حقیقت

در تعارض اطلاعات، ترتیب بررسی:
1. فایل canonical و Commit پذیرفته‌شده در شاخه اصلی؛
2. ADR پذیرفته‌شده و تصمیم ثبت‌شده؛
3. نتیجه آزمون/CI و شواهد قابل بازبینی؛
4. Issue، Pull Request و مستندات نسخه‌دار؛
5. منابع بیرونی معتبر با تاریخ و نسخه؛
6. یادداشت یا خلاصه مکالمه؛
7. پیشنهاد یا حدس ثبت‌نشده.

یک متن در چت صرفاً به دلیل گفته‌شدن، تصمیم رسمی پروژه نیست.

## 4. آنچه باید در مخزن بماند

- منشور، مأموریت، محدوده و معیار موفقیت؛
- معماری محصول و Runtime؛
- Taxonomy و Schemaها؛
- شناسه‌ها و روابط canonical؛
- منابع و provenance؛
- تصمیم‌ها و دلایل رد گزینه‌ها؛
- برنامه انتشار و وضعیت کار؛
- دستورالعمل نصب، کاربری و توسعه؛
- گزارش آزمون و CI؛
- محدودیت‌ها، ریسک‌ها و کارهای NOT_RUN/BLOCKED؛
- اطلاعات نسخه و آخرین Commit معتبر.

## 5. بازیابی روی رایانه جدید

1. Git و Python 3.11+ را نصب کنید.
2. مخزن را clone کنید.
3. README.md را بخوانید.
4. docs/USER_DOCUMENTATION_INDEX.md را باز کنید.
5. docs/CONTEXT_CONTINUITY.md و docs/IMPLEMENTATION_PLAN.md را برای وضعیت توسعه بخوانید.
6. Runtime را طبق docs/USER_INSTALLATION.md اجرا کنید.
7. Branch و Commit فعلی را بررسی کنید.
8. وضعیت CI و Pull Requestهای باز را بررسی کنید.

~~~bash
git clone https://github.com/metsam-mastem/EKTA.git
cd EKTA
git branch --show-current
git rev-parse HEAD
git status --short
~~~

## 6. بازیابی بدون Git

اگر Git نصب نیست، از صفحه مخزن GitHub گزینه Download ZIP را برای شاخه موردنظر انتخاب و فایل را استخراج کنید. این روش برای مشاهده و اجرای snapshot مناسب است، اما تاریخچه Commit و Branch و امکان Pull را در اختیار نمی‌گذارد. برای مشارکت و توسعه، Git را نصب کنید.

## 7. پشتیبان‌گیری\n\nمیزکار عملیاتی در `/workspace` امکان ساخت ZIP از مسیرهای منتخب و مرحله‌بندی پیش‌نمایش یک ZIP بازیابی را دارد. این بسته، Git history و Branchها را شامل نمی‌شود و جایگزین clone کامل نیست. بازیابی در نسخه فعلی به‌صورت خودکار انجام نمی‌شود؛ بسته فقط پس از بررسی امنیتی در `.ekta/workspace/restore-staging/` نگهداری می‌شود. راهنمای جزئیات در [WORKSPACE_GUIDE.md](WORKSPACE_GUIDE.md) است.\n\n

حداقل یک نسخه مستقل از موارد زیر نگه دارید:
- clone کامل مخزن همراه .git؛
- تغییرات محلی Commit‌نشده؛
- داده‌ها و فایل‌های اختصاصی که هنوز وارد مخزن نشده‌اند؛
- گزارش‌های آزمون و خروجی‌های مهم غیرقابل‌بازتولید.

پیشنهاد عملی: یک clone دوم روی دیسک یا محل جداگانه نگه دارید و دوره‌ای git fetch و مقایسه وضعیت را انجام دهید. خروجی‌های مشتق‌شده مانند cache و index در صورت قابل‌بازتولید بودن، اولویت پشتیبان‌گیری پایین‌تری دارند.

## 8. ادامه کار توسط انسان یا AI دیگر

عامل جدید باید:
1. README و منشور را بخواند؛
2. مستندات کاربری یا توسعه‌دهنده متناسب با وظیفه را بخواند؛
3. Branch، Commit، وضعیت Working Tree و CI را بررسی کند؛
4. Issue/PR و تصمیم‌های پذیرفته‌شده را بررسی کند؛
5. کد واقعی را پیش از ادعای قابلیت بخواند؛
6. کار را در Branch مستقل انجام دهد؛
7. آزمون‌ها و validatorها را اجرا کند؛
8. Commit/PR، شواهد و محدودیت‌ها را در مخزن ثبت کند.

برای دستور دقیق‌تر به docs/AGENT_ONBOARDING.md مراجعه کنید.

## 9. چه چیزی در مخزن عمومی ذخیره نشود؟

رمز عبور، کلید API، Access Token، کلید خصوصی، داده شخصی یا محرمانه، اسناد دارای محدودیت انتشار و کپی کامل استانداردهای دارای حق نشر را Commit نکنید.

## 10. آزمون استقلال

پروژه زمانی از چت مستقل است که فردی تازه‌وارد، بدون مشاهده مکالمه قبلی بتواند:
- ماهیت و محدوده EKTA را بفهمد؛
- نسخه و وضعیت جاری را پیدا کند؛
- نصب و اجرا کند؛
- جست‌وجو و شناسنامه‌ها را مشاهده کند؛
- بداند چه چیزی پشتیبانی نمی‌شود؛
- دانش جدید را طبق گردش کار ثبت کند؛
- آزمون‌ها را اجرا و تغییر را بازبینی کند؛
- کار را از آخرین نقطه ثبت‌شده ادامه دهد.

این اسناد برای تحقق معیار طراحی شده‌اند؛ آزمون نهایی onboarding کاربر تازه باید جداگانه اجرا و نتیجه آن ثبت شود.
