# EKTA چیست؟ — معرفی جامع پروژه و محصول

نام: Engineering Knowledge & Techniques Atlas (EKTA)  
تعریف محصول: Engineering Knowledge Operating Environment  
نسخه Runtime مورد بحث: 0.2  
وضعیت منشور: APPROVED — 2026-11-23

## 1. تعریف کوتاه

EKTA محیطی برای سازمان‌دهی، کشف، فهم، اتصال، ارزیابی و استفاده از دانش مهندسی است. هدف آن تبدیل دانش پراکنده در مستندات فنی، استانداردها، مقالات، مخازن کد، طراحی‌ها، تجربه‌ها و روش‌های اجرایی به مجموعه‌ای ساخت‌یافته، قابل جست‌وجو، رابطه‌مند و قابل بازبینی است.

EKTA صرفاً واژه‌نامه نیست. در کنار تعریف، زمینه، نقش، سازوکار، اجزا، ورودی/خروجی، وابستگی‌ها، روابط، پیاده‌سازی‌ها، شواهد، محدودیت‌ها و روش اعتبارسنجی را نیز مدل می‌کند.

## 2. مسئله‌ای که حل می‌کند

دانش مهندسی میان مستندات رسمی، استانداردها، مقالات، کتاب‌ها، مخازن Git، مستندات سازندگان، آموزش‌ها و تجربه افراد پراکنده است. اصطلاح مشابه ممکن است در لایه‌های مختلف معنای متفاوت داشته باشد؛ در عین حال چند اصطلاح متفاوت ممکن است به نقش‌های نزدیک اشاره کنند.

این پراکندگی باعث تکرار پژوهش، سردرگمی اصطلاحی، از دست رفتن منشأ ادعا، دشواری مقایسه و فاصله میان دانستن و اقدام می‌شود. EKTA برای کاهش این هزینه‌ها ساخته می‌شود؛ نه برای جایگزینی قضاوت مهندسی، استانداردهای رسمی یا آزمون مستقل.

## 3. چرا اطلس، نه صرفاً دانشنامه؟

دانشنامه معمولاً صفحه‌های مجزا دارد. اطلس علاوه بر رکورد، موقعیت و رابطه آن با سایر اجزا را نیز مدل می‌کند:
- مفهوم در کدام قلمرو و لایه قرار دارد؟
- زیرمجموعه یا تخصص کدام مفهوم است؟
- به چه چیزی وابسته است یا از چه چیزی استفاده می‌کند؟
- چه چیزی آن را پیاده‌سازی می‌کند؟
- چه جایگزین‌ها و رقبایی دارد؟
- چه شواهدی ادعاهای آن را پشتیبانی می‌کنند؟

هویت هر مفهوم مستقل است، اما دانش به شکل جزیره‌ای نگهداری نمی‌شود.

## 4. چهار فضای محصول

### DISCOVERY — کشف
شروع از سؤال، مسئله یا اصطلاح؛ گردآوری منابع؛ تشخیص اصطلاحات؛ استخراج مفاهیم کاندید؛ تعیین محدوده و عدم قطعیت.

### ENCYCLOPEDIA — دانشنامه ساخت‌یافته
ثبت مفاهیم canonical، تعریف، مرز، طبقه‌بندی، اجزا، سازوکار، روابط، شواهد و نسخه.

### DECISION LAB — آزمایشگاه تصمیم
مقایسه گزینه‌ها بر اساس معیارها، محدودیت‌ها، هزینه، ریسک، عملکرد و Trade-off؛ ثبت فرض‌ها و تصمیم. این فضای کامل در Runtime 0.2 پیاده‌سازی نشده است.

### EXECUTION LAB — آزمایشگاه اجرا
تبدیل دانش و تصمیم به روش اجرا، Playbook، چک‌لیست، آزمایش، نمونه‌سازی و شواهد آزمون. این فضای کامل در Runtime 0.2 پیاده‌سازی نشده است.

## 5. چرخه ارزش

Question → Discovery → Concept → Relationships → Evidence → Decision → Execution → Verification → Reusable Knowledge

1. مسئله یا سؤال مشخص می‌شود.
2. منابع و اصطلاحات مرتبط پیدا می‌شوند.
3. مفهوم یا سند کاندید ثبت می‌شود.
4. هویت و طبقه‌بندی canonical تعیین می‌شود.
5. روابط نوع‌دار و منشأ شواهد ثبت می‌شوند.
6. کیفیت و اعتبار ادعاها بررسی می‌شود.
7. تصمیم یا روش اجرا از دانش استخراج می‌شود.
8. نتیجه با معیار و شواهد آزموده می‌شود.
9. یادگیری به دانش قابل استفاده مجدد تبدیل می‌شود.

نسخه فعلی بخشی از این چرخه، به‌ویژه جست‌وجو و مشاهده را پشتیبانی می‌کند؛ کل چرخه هنوز به‌صورت نرم‌افزار تعاملی پیاده نشده است.

## 6. مدل طبقه‌بندی

EKTA یک لایه ناوبری و سه محور مستقل دارد:
- Engineering Territory: ۲۶ قلمرو کلان برای ناوبری و سنجش پوشش.
- Engineering Domain: ۲۵ حوزه عملیاتی برای طبقه‌بندی تخصصی.
- Engineering Layer: جایگاه مفهوم در لایه‌های مهندسی.
- Knowledge / Technique Type: نوع رکورد، مانند Concept، Architecture، Pattern، Method یا Standard.

قلمرو کلان و حوزه تخصصی یکی نیستند. یک مفهوم می‌تواند به چند حوزه و چند لایه مرتبط باشد. رجیستری‌های canonical در taxonomy/ نگهداری می‌شوند.

## 7. شناسنامه مهندسی

شناسنامه مطلوب، متناسب با نوع رکورد، این ابعاد را پوشش می‌دهد:

| بُعد | پرسش |
|---|---|
| Identity | نام canonical، شناسه و نام‌های جایگزین چیست؟ |
| Definition | تعریف دقیق و مرز آن چیست؟ |
| Purpose | چرا وجود دارد و چه مسئله‌ای را حل می‌کند؟ |
| Role | چه مسئولیتی در سیستم دارد؟ |
| Classification | قلمرو، حوزه، لایه و نوع آن چیست؟ |
| Architecture | اجزا، مرزها و رابط‌ها کدام‌اند؟ |
| Mechanism | چگونه کار می‌کند؟ |
| Lifecycle | حالت‌ها و چرخه عمر آن چیست؟ |
| Input / Output | چه ورودی، خروجی، رویداد و خطایی دارد؟ |
| Dependencies | به چه چیزهایی وابسته است؟ |
| Relations | چه چیزهایی را اجرا، کنترل، توسعه یا پیاده‌سازی می‌کند؟ |
| Implementation | نمونه‌های پیاده‌سازی و نسخه‌هایشان کدام‌اند؟ |
| Trade-offs | هزینه‌ها، محدودیت‌ها و مزایا چیست؟ |
| Verification | چگونه می‌توان ادعا یا عملکرد را آزمود؟ |
| Evidence | هر ادعا بر چه منبعی تکیه دارد؟ |

همه انواع رکورد الزاماً تمام فیلدها را به یک اندازه ندارند. Schema نوع رکورد مرجع است؛ داده نامعلوم نباید با حدس پر شود.

## 8. معماری محصول

اصل طراحی: محتوای canonical در مخزن نسخه‌پذیر نگهداری می‌شود؛ Runtime آن را می‌خواند و نماهای مشتق‌شده می‌سازد.

~~~text
Canonical Git Repository
  ├── taxonomy/
  ├── encyclopedia/
  ├── docs/ + research/ + references/
  └── schemas/ + templates/
           |
           v
Content Loader and Validators
           |
           v
Knowledge Services
  ├── Search and Facets
  ├── Concept Lookup
  ├── Taxonomy
  └── Graph Projection
           |
           v
FastAPI / OpenAPI
           |
           v
Persian RTL Browser Workbench
~~~

Runtime 0.2 از Python 3.11+، FastAPI، Uvicorn، PyYAML، JSON Schema و HTML/CSS/JavaScript استفاده می‌کند. این انتخاب نسخه فعلی است، نه تعهد دائمی معماری.

- رابط مرورگر فارسی و راست‌به‌چپ؛

- نمایش نتایج با خلاصه، امتیاز و مسیر منبع؛
- مشاهده محتوای شناسنامه و سند؛

## 10. قابلیت‌هایی که هنوز وجود ندارند

در Runtime 0.2، رابط فقط خواندنی است. ورود مستقیم فایل از UI، استخراج خودکار PDF/Office، OCR، ASR، تحلیل تصویر/ویدئو، ویرایش رکورد در UI، حساب کاربری، چندکاربره، همگام‌سازی ابری، جست‌وجوی معنایی، پاسخ‌گویی AI، گراف تعاملی کامل، Decision Lab و Execution Lab کامل، بسته Android و نصب‌کننده یک‌کلیکی وجود ندارند.

برای ثبت دانش جدید در وضعیت فعلی، باید رکوردهای canonical را با قالب‌ها در مخزن ایجاد یا اصلاح کرد، سپس اعتبارسنجی و بازبینی Git انجام داد.

## 11. کاربردها و مخاطبان

- مهندس و معمار: فهم وابستگی‌ها، مرزها و گزینه‌های طراحی.
- پژوهشگر: سازمان‌دهی منابع، اصطلاحات و شواهد.
- توسعه‌دهنده: اتصال مفهوم به API، کد، کتابخانه و آزمون.
- مدیر فنی: حفظ تصمیم‌ها، استانداردها و دانش تیم.
- دانشجو: ساخت مسیر یادگیری و نقشه مفاهیم.
- تیم AI و Retrieval: مصرف داده‌های ساخت‌یافته و ارجاع‌پذیر، پس از تعریف قرارداد و کنترل دسترسی مناسب.

نمونه کاربردها: فهم تفاوت Runtime، Engine، Controller و Manager؛ بررسی یک فناوری از لایه سخت‌افزار تا نرم‌افزار؛ یافتن پیاده‌سازی‌های متن‌باز و ثبت مجوز و وضعیت نگهداری؛ ساخت نقشه وابستگی؛ مقایسه معماری‌ها؛ تبدیل یافته پژوهش به Playbook و معیار پذیرش.

## 12. اصول اعتماد و کیفیت

- شناسه‌ها پایدار و غیرقابل استفاده مجدد هستند.
- ادعا از تفسیر، پیشنهاد و نتیجه آزمون تفکیک می‌شود.
- منبع، نسخه و تاریخ دسترسی ثبت می‌شوند.
- روابط با Predicate کنترل‌شده تعریف می‌شوند.
- unresolved بودن رابطه پنهان یا حدس زده نمی‌شود.
- IMPLEMENTED با VALIDATED یکسان نیست.
- محتوای دارای محدودیت حق نشر بدون مجوز کپی نمی‌شود.
- ادعای پوشش کامل نیازمند معیار اندازه‌گیری است.
